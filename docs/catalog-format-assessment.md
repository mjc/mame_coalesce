# Catalog format assessment (MAMEC-36)

This is a bounded adapter decision, not a claim that the three preservation projects share one publisher model. The four checked-in examples are synthetic CC0 fixtures built from each project's published field vocabulary and workflow documentation. They contain no ROM/disc bytes and do not reproduce upstream records. The manifest pins their exact bytes and records provenance and open limits.

## Decision matrix

| Ecosystem / pinned sample | Syntax, publisher, version and scope | Requirement semantics and candidate normalized facts | Source-only fields / extension retention | Companion association | Terms, unsupported cases, malformed/partial handling |
|---|---|---|---|---|---|
| No-Intro DAT-o-MATIC P/C XML — `no-intro-pc-xml-synthetic` | DAT-o-MATIC exposes Standard DAT, P/C, P/C XML and DB exports. The naming reference documents P/C XML fields such as `name`, `namealt`, `region`, `languages`, `version`, `bios`, `clone`, and `mergeof`. The synthetic fixture uses an XML/Logiqx-like envelope to pin those documented field concepts; it intentionally does **not** claim the exact production P/C XML envelope or full schema. Snapshot date/filter and archive IDs belong to source interpretation, not parser-format identity. | ROM name/size/CRC/SHA-1 are ordinary expected-content claims. `clone` is a source archive number (`P` or a parent archive number), not a parent title; keep it as an opaque source ID until a same-snapshot ID map resolves it. `mergeof` is likewise not the Logiqx ROM `merge` relation. Region/language/BIOS are release metadata, not requirement hashes. | Preserve `namealt`, region/languages, parent archive IDs, merge IDs, export filters, and every unrecognized attribute. Missing export fields stay unknown. | No separate companion is necessary for the selected P/C XML slice. If a later export adds external records, require an explicit source archive ID in the same pinned export; a similar title is only a candidate. | No-Intro's current data-usage license is scoped to rights it controls and does not grant third-party rights. This fixture is synthetic CC0 instead. The public reference leaves “Dat format” details marked TODO, so exact serialization, ID stability, filter behavior, and malformed export behavior remain implementation-time verification items. Reject malformed XML/duplicate or unresolved IDs as diagnostics; do not fabricate parent names. |
| TOSEC DAT — `tosec-logiqx-xml-synthetic` | TOSEC announced that its DATs moved to XML in the 2015-06-04 release. The pinned fixture uses the already-supported Logiqx XML syntax; the project-specific convention is the opaque filename/title string and release header (`TOSEC-v…`). A snapshot represents the exact exported DAT/version; filtering is not inferred from an absent set. | ROM names, sizes and checksums map to expected components. The TNC title combines independently meaningful title/version/date/publisher/system/region/status descriptors. Initially preserve the whole source name; do not parse it into canonical game identity or infer dump confidence from `[b]`. | Preserve release/header metadata, the exact TNC name, and unmodeled per-record fields. Future TNC parsing requires a pinned revision and token-preserving grammar; separators/parentheses in names are not a stable universal field encoding. | Cue sheets, playlists, or other sidecars are independent documents unless they explicitly reference exact member names under a shared source/export scope. A shared basename alone cannot associate them. | Official TNC revision 4 is the pinned naming reference; official release notes establish XML output. Only a synthetic CC0 DAT is included. This sample does not exercise every TOSEC branch (ISO, PIX, magazines, multisets), historical DAT version, CUE syntax, or TNC edge case. XML well-formedness and missing hashes can be handled by the existing parser/import contract; source-specific parse failures should retain locations and raw fields. |
| Redump DAT — `redump-track-dat-synthetic` | Redump describes itself as a disc preservation database, with DAT generation secondary to its database. The pinned synthetic Logiqx XML entry contains one disc identity/serial and two ordered track-file hash claims. Track numbers appear in the DAT filenames; the companion CUE supplies track modes and index layout. The source entry/export version and selection scope must be retained as snapshot metadata when available. | Each track is a separately hashed file requirement; order, track number/type, size and CRC/MD5/SHA-1 matter. The disc is not interchangeable with a single cartridge-like ROM or an automatically executable image. Track claims should not be collapsed into one digest. | Preserve serial, region/title descriptors, per-track metadata, dump comments and every field not represented by the current schema. Universal hashes and lead-in/lead-out tracks need explicit scopes; a hash in comments is not a normal file hash. | The exact CUE `FILE` references are explicit edges to track names. Associate only when references resolve uniquely within the selected disc/source snapshot and track structure is consistent. A CUE basename match or filename similarity alone is only a candidate; CUE content has no hashes that prove the referenced bytes. Preserve the CUE document and its `TRACK`/`INDEX` structure separately. | Redump's own guides document track hashes and CUE sheets; Redump's wiki states catalog metadata is publicly usable, but third-party rights still apply. This fixture uses invented identifiers/hashes and is CC0. Unsupported: multisession, pregap/lead-in/lead-out claims, universal hash, subchannel/protection details, alternate dumps, and malformed CUE recovery. A partial CUE can be retained and diagnosed, but must not silently become a complete disc snapshot. |
| Redump CUE companion — `redump-cue-companion-synthetic` | A separate cue sheet from the same synthetic package; its file references link to the DAT sample's two exact track names. It has no independent catalog version or disc identity in this minimal sample, so that context is inherited only through explicit acquisition/package provenance and validated references. | `FILE`, `TRACK`, mode, `INDEX 00`, and `INDEX 01` describe ordered layout, not expected file hashes. They complement rather than replace DAT track requirements. | Preserve source bytes, line/column, all REM/comments, filename spelling, track mode and index timing. Do not synthesize missing DAT hashes from the cue. | Require the same trusted acquisition/package scope plus unique exact `FILE`-to-track references. If more than one disc matches, leave an unresolved association candidate. Never join based only on similar cue/dat filenames. | CC0 synthetic. Real CUE dialects may include quoting, multiple files per track, pregaps, sessions, mixed modes, and vendor extensions. This fixture pins only one simple two-track shape; malformed references produce diagnostics and no complete association. |

## Chosen next increment

Implement **No-Intro DAT-o-MATIC P/C XML metadata/relationship support first** under MAMEC-32/34's shared import boundary. It is the clearest bounded extension of the currently supported Logiqx XML syntax and has explicit source fields for parent archive number, language, region and BIOS. Keeping the numeric parent reference source-scoped avoids imposing TOSEC's filename convention or Redump's track/media semantics on common storage. Reuse raw document retention and extension capture; normalize only fields whose exact export representation is pinned.

Before MAMEC-50 treats this as a production dialect, obtain an authorized P/C XML sample or confirm the exact synthetic serialization against a current export; the public No-Intro naming reference documents custom field names but marks the overall DAT format TODO. Parent IDs that do not resolve uniquely in the same export remain source assertions, not guessed links.

Redump track/CUE semantics should be assessed after the shared domain can represent ordered track roles and companion documents without lossy ROM coercion. TOSEC's basic XML syntax already overlaps the Logiqx adapter; its source-specific TNC interpretation can remain raw metadata until a consumer needs typed fields.
