# Catalog format assessment (MAMEC-36)

This is a bounded adapter decision, not a claim that the three preservation projects share one publisher model. The four checked-in examples are synthetic CC0 fixtures built from each project's published field vocabulary and workflow documentation. They contain no ROM/disc bytes and do not reproduce upstream records. The manifest pins their exact bytes and records provenance and open limits.

The next schema design is recorded in
[Catalog schema redesign from all input formats](catalog-schema-redesign.md).
The 2026-09-30 corpus audit identifies the downloaded `pc-engine.xml` as
OfflineList-style `<dat>/<configuration>/<games>` XML, not production
DAT-o-MATIC P/C XML. PureDOS contains additional source/track/patch structures
beyond baseline Logiqx. Those inputs do not establish complete coverage of the
named adapters. Supported specification fields require native typed relations;
the source-only/extension choices in the historical assessment below do not
supersede that requirement. The user accepted the latest 471,031,808-byte MAME
database as the size baseline; cross-format schema and query correctness now
take precedence over the earlier mandatory smaller-than-XML threshold.

The larger user-supplied metadata corpus is now in the checkout-local,
git-excluded `local/catalog-data/2026-09-30` directory (5,685 files; 1.1 GiB
apparent size). Its No-Intro DAT and PC packs carry v3/v4 schemaLocations;
schemaLocation is not proof of strict XSD conformance, and v3-labelled records
include several observed compatibility cases. “PC” here is a parent-clone pack,
not proof of the separate DAT-o-MATIC P/C XML export. The 4,743-file TOSEC pack
is Logiqx XML, including PDF and disc assets encoded as `<rom>` entries. The
274 No-Intro database XML exports and the
Family Computer Disk System sample instead nest archive, source, and file
records; some contain sibling `<header>` and `<datafile>` roots. The Xbox 360
export has six NUL characters; accept it only through narrow in-memory recovery
after decoding, with original-location diagnostics and byte-exact external
source retention. Full field and cardinality evidence is in
[catalog-schema-redesign.md](catalog-schema-redesign.md) and the corresponding
tickets MAMEC-60 and MAMEC-61. The DAT-o-MATIC P/C XML
export itself remains unacquired and is tracked separately in MAMEC-56.

## Decision matrix

| Ecosystem / pinned sample | Syntax, publisher, version and scope | Requirement semantics and candidate normalized facts | Source-only fields / extension retention | Companion association | Terms, unsupported cases, malformed/partial handling |
|---|---|---|---|---|---|
| No-Intro DAT-o-MATIC P/C XML — `no-intro-pc-xml-synthetic` | DAT-o-MATIC exposes Standard DAT, P/C, P/C XML and DB exports. The naming reference documents P/C XML fields such as `name`, `namealt`, `region`, `languages`, `version`, `bios`, `clone`, and `mergeof`. The synthetic fixture uses an XML/Logiqx-like envelope to pin those documented field concepts; it intentionally does **not** claim the exact production P/C XML envelope or full schema. Snapshot date/filter and archive IDs belong to source interpretation, not parser-format identity. | ROM name/size/CRC/SHA-1 are ordinary expected-content claims. `clone="P"` marks the synthetic parent; the child's numeric `clone="1042"` reference remains unresolved because the fixture has no archive-number field identifying the parent row. `mergeof` remains an opaque source string; the reference describes it only as MAME-like merging. Region/language/BIOS are release metadata, not requirement hashes. | Preserve `namealt`, region/languages, clone and mergeof tokens, export filters, and every unrecognized attribute. Missing export fields stay unknown. | No separate companion is necessary for the selected P/C XML slice. Do not resolve numeric references unless a pinned export exposes the corresponding archive number in the same snapshot; a similar title is only a candidate. | No-Intro's data-usage license is scoped to rights it controls and does not grant third-party rights. This fixture is synthetic CC0 instead. The public reference leaves “Dat format” details marked TODO, so exact serialization, ID stability, filter behavior, and malformed export behavior remain implementation-time verification items. Preserve unresolved parent IDs as source assertions; do not fabricate parent names. |
| TOSEC DAT — `tosec-logiqx-xml-synthetic` | TOSEC announced that its DATs moved to XML in the 2015-06-04 release. The pinned fixture uses the already-supported Logiqx XML syntax; the project-specific convention is the opaque filename/title string and release header (`TOSEC-v…`). A snapshot represents the exact exported DAT/version; filtering is not inferred from an absent set. | ROM names, sizes and checksums map to expected components. The TNC title combines independently meaningful title/version/date/publisher/system/region/status descriptors. Initially preserve the whole source name; do not parse it into canonical game identity or infer dump confidence from `[b]`. | Preserve release/header metadata, the exact TNC name, and unmodeled per-record fields. Future TNC parsing requires a pinned revision and token-preserving grammar; separators/parentheses in names are not a stable universal field encoding. | Cue sheets, playlists, or other sidecars are independent documents unless they explicitly reference exact member names under a shared source/export scope. A shared basename alone cannot associate them. | Official TNC revision 4 is the pinned naming reference; official release notes establish XML output. Only a synthetic CC0 DAT is included. This sample does not exercise every TOSEC branch (ISO, PIX, magazines, multisets), historical DAT version, CUE syntax, or TNC edge case. XML well-formedness and missing hashes can be handled by the existing parser/import contract; source-specific parse failures should retain locations and raw fields. |
| Redump DAT — `redump-track-dat-synthetic` | Redump describes itself as a disc preservation database, with DAT generation secondary to its database. The pinned synthetic Logiqx XML entry contains two ordered track-file hash claims and a free-text description with an invented serial-like string; that string is not a declared serial field. Track numbers appear in the DAT filenames; the companion CUE supplies track modes and index layout. The source entry/export version and selection scope must be retained as snapshot metadata when available. | Each track is a separately hashed file requirement; order, track number/type, size and CRC/MD5/SHA-1 matter. The disc is not interchangeable with a single cartridge-like ROM or an automatically executable image. Track claims should not be collapsed into one digest. | Preserve the description verbatim, region/title descriptors, per-track metadata, dump comments and every field not represented by the current schema. Do not interpret serial-like text as a serial unless an authoritative export defines that field. Universal hashes and lead-in/lead-out tracks need explicit scopes; a hash in comments is not a normal file hash. | The exact CUE `FILE` references are explicit edges to track names. Associate only when references resolve uniquely within the selected disc/source snapshot and track structure is consistent. A CUE basename match or filename similarity alone is only a candidate; CUE content has no hashes that prove the referenced bytes. Preserve the CUE document and its `TRACK`/`INDEX` structure separately. | Redump's own guides document track hashes and CUE sheets; Redump's wiki states catalog metadata is publicly usable, but third-party rights still apply. This fixture uses invented identifiers/hashes and is CC0. Unsupported: structured serial extraction from this description, multisession, pregap/lead-in/lead-out claims, universal hash, subchannel/protection details, alternate dumps, and malformed CUE recovery. A partial CUE can be retained and diagnosed, but must not silently become a complete disc snapshot. |
| Redump CUE companion — `redump-cue-companion-synthetic` | A separate cue sheet from the same synthetic package; its file references link to the DAT sample's two exact track names. It has no independent catalog version or disc identity in this minimal sample, so that context is inherited only through explicit acquisition/package provenance and validated references. | `FILE`, `TRACK`, mode, `INDEX 00`, and `INDEX 01` describe ordered layout, not expected file hashes. They complement rather than replace DAT track requirements. | Preserve source bytes, line/column, all REM/comments, filename spelling, track mode and index timing. Do not synthesize missing DAT hashes from the cue. | Require the same trusted acquisition/package scope plus unique exact `FILE`-to-track references. If more than one disc matches, leave an unresolved association candidate. Never join based only on similar cue/dat filenames. | CC0 synthetic. Real CUE dialects may include quoting, multiple files per track, pregaps, sessions, mixed modes, and vendor extensions. This fixture pins only one simple two-track shape; malformed references produce diagnostics and no complete association. |

## Chosen next increment

Per-format completeness is tracked for the unverified DAT-o-MATIC P/C XML export (MAMEC-56), pinned Logiqx XML (MAMEC-57), ClrMamePro text (MAMEC-58), MAME software-list XML (MAMEC-59), the No-Intro DAT v3/v4 dialect (MAMEC-60), and No-Intro database-export XML (MAMEC-61). The active MAMEC-55 work covers MAME machine list XML and cross-format storage compaction, including a shared catalog-asserted content UUID for eligible whole-file SHA-1/SHA-256 evidence while preserving each source occurrence separately.

The active typed-relational completeness work is tracked in [MAMEC-55](https://lific.mjc.lol/MAMEC/issues/MAMEC-55), not the archived adapter roadmap below. No-Intro coverage persists game `id`, `<description>`, and ROM `md5` as typed query facts, in addition to the existing common hashes. This is grounded in a current PC entry whose XML view contains those fields ([entry/XML view](https://data.spludlow.co.uk/no-intro/no-intro/IBM%20-%20PC%20and%20Compatibles%20(Digital)%20(Unknown)/Wake%20(Unknown)%20(Windows))). Logiqx coverage stores root build/debug/file-name/SHA-1 and header name/description/version/date/author/email/homepage/URL/comment/category, plus game source-file/BIOS/board/rebuild-target/description/year/manufacturer, in relational tables included in snapshot diffs. MAME listxml coverage now persists every declared 0.289 machine-child family, including displays, controls, conditions, driver/features, devices/slots/software lists, and RAM options, together with the device-reference tag and DTD defaults. Ordered nested facts and these typed rows participate in snapshot diffs. Remaining format-completeness work is tracked separately for [No-Intro](https://lific.mjc.lol/MAMEC/issues/MAMEC-56), [Logiqx](https://lific.mjc.lol/MAMEC/issues/MAMEC-57), and [ClrMamePro](https://lific.mjc.lol/MAMEC/issues/MAMEC-58). The broader ticket remains open for No-Intro schema verification, remaining fields, JSON removal, compact source facts, and the fresh full-file size proof.

MAMEC-50 implemented only the checked-in synthetic documented-field projection. The naming reference documents custom field names but leaves the overall DAT serialization incomplete. Keep each export field source-scoped and avoid inferring values from filenames or descriptive text. Now that actual exports expose per-game IDs, resolve numeric clone references only after the parser and snapshot model persist the full ID map and tests prove an unambiguous within-document target; do not guess from titles. MAMEC-55 remains responsible for the remaining typed fields and relational snapshot-diff coverage.

Redump track/CUE semantics should be assessed after the shared domain can represent ordered track roles and companion documents without lossy ROM coercion. TOSEC's basic XML syntax already overlaps the Logiqx adapter; its source-specific TNC interpretation can remain raw metadata until a consumer needs typed fields.
