# No-Intro candidate slice

Status: design candidate only. This file does not authorize production schema or parser changes. The DDL depends on `shared.sql` and `relationships.sql`; `no_intro-owners.tsv` lists registry-bearing typed placements and is consumed by the main assembler. The common `catalog_sets` row owns game identity/name/root placement. A native game payload row is not a second element owner. `catalog_media_entries` owns shared media identity; each format claim owns its one actual parent and child order.

## Physical roots and diagnostic coordinates

Root/document/header candidates carry the common proposed diagnostic column names: `extent_view`, `extent_start`, `extent_end`, `location_view`, `start_line`, `start_column`, `end_line`, `end_column`, and `column_convention`. Extent endpoints are an all-or-none interval. Location start and end pairs are independently nullable so an observed opening coordinate does not fabricate an end. Whenever `location_view` is populated, `column_convention` must be non-NULL `one_based_unicode_scalar`; nullable document/header locations require both fields NULL together. A populated location uses one-based Unicode-scalar columns. Each canonical header requires at least one populated diagnostic system; document/datafile/header owners remain distinct and no root is represented as an ordinary source element. The export document may retain neither until root-start capture is available, which remains an explicit capture gap rather than an invented extent.

Current capture is incomplete for containment: flat DAT currently exposes the datafile opening location, not a complete datafile extent. The export reader retains the document EOF and datafile opening location, not a distinct complete datafile-root extent; the candidate has the explicit nullable columns for new capture. The source-free P/C root has an opening location but no verified interval contract in the policy read. Header/game/ordinary export children have current decoded-text element extents where the reader exposes them. These decoded-text extents are not silently relabeled as byte offsets, and ordinary child opening-only locations do not prove full containment. A fully populated/verified interval, exact source-view mapping, and range/containment checks remain integration and parser-evidence work. The optional extent columns do not claim otherwise.

Flat No-Intro DAT is XML parsed with `XmlUnicodeScalars`; its root location uses `transport_decoded_xml_text` and `one_based_unicode_scalar`. `decoded_dat_text` is reserved for the ClrMamePro DAT text lexer and must not be inferred from a `.dat` filename. This candidate name matches DOC-21's root-location view and the parser's coordinate mapping. Export and synthetic P/C XML locations also use `transport_decoded_xml_text`; a byte extent view is populated only with a verified original/transport byte mapping. Null extent means unavailable. Main's root-diagnostic integration should preserve these distinctions when it builds linked diagnostics.

## Exact native field and position inventories

### Flat DAT v3/v4

Supported interpretations are strict v3, strict v4, compatible v3 and compatible v4. The candidate retains typed root/header facts, twelve possible singleton header text children (`id,name,description,version,date,author,homepage,url,trademarks,piracy,subset,comment`), optional `clrmamepro` (`forcenodump,header`) and `romcenter` (`plugin`) directive attributes, game attributes (`name,id,cloneof,cloneofid`), game children (`description`, repeated `category`, compatible-only repeated `game_id`, repeated `release(name,region)`), and ROM attributes (`name,size,crc,md5,sha1,sha256,status,serial,header,date,mia`). Values live once on their typed owner; attribute coordinates/order live once in the named `*_field_positions` relations; valid digest bytes live once in `hash_values` via `catalog_entry_hashes`. `cloneof`/`cloneofid` are distinct unresolved declarations. ROM media ID equals its source-element ID.

Field presence follows the parser contract: absent nullable fields have no position, present empty strings retain `''` and a position. Requiredness and multiplicity are mode-specific, not SQL defaults: `id/name/description/version` header children always; `author` additionally in strict modes; strict v3 excludes `trademarks/piracy`; `comment` is compatible-only; one required description per game; strict exactly one ROM and compatible at least one; release `name/region` are required when a release exists. Strict ROM `size/crc/md5/sha1` are required; compatible fields are optional. DAT field codes use the exact wire spellings above and occurrence 0 because these attributes are singleton.

The separate XSI owners retain only the four documented expanded-name fields `schemaLocation`, `noNamespaceSchemaLocation`, `type`, `nil`, scoped to the actual declaring element. Ordinary complex/root owners exclude `type`; simple text owners carry `resolved_type_kind` only when a recognized type attribute is present. Candidate accepted resolved types are `int,short,byte,string,normalizedString,token,language,Name,NCName,NMTOKEN,ID,IDREF,ENTITY`; header `id` uses the integer subset and other simple fields use the string subset. Original QName spelling, expanded field code, value and lexical ordinal are distinct facts. Schema hints and explicit nil values are retained only after parser validation; compatible nil accepts collapsed `false/0`, strict modes reject any explicit nil, and both modes reject contradictory recognized schema revisions. XSI position ordinals share the tag's lexical attribute domain with the native position table; main must generate cross-table ordinal checks.

Strict XSD-derived cardinality, order and lexical checks remain reading-rule/import policy. Compatible parsing skips unknown elements and ignores unknown ordinary attributes; neither branch justifies a catch-all raw-attribute store. Unknown XSI-namespace fields are outside the four-field retained set.

### Synthetic P/C fixture projection

This is the repository's synthetic `<datafile>` fixture grammar, not authentic DAT-o-MATIC P/C. Header text child kinds are exactly `name`, `description`, and optional singleton `version`; repeated names/descriptions remain distinct ordered elements. The only game text child is optional singleton `description`. Header/game child orders are mixed domains; root header and games share the root group order. A present-empty text child is a row with `''`.

Game attribute positions have exactly nine codes: `name,id,namealt,region,languages,version,bios,clone,mergeof`. `catalog_sets.set_name` is the sole name value; `no_intro_pc_games` has the archive ID and optional scalar facts; clone marker/link and merge link retain their own declaration; language tokens alone live in `no_intro_pc_languages` as zero-based comma-split/trimmed nonempty tokens. Missing versus present-empty `languages` is determined by the `languages` position, not a duplicate presence bit. Required/name, numeric-reference and `clone=P` marker rules follow DOC-9; leading-zero accepted references remain text.

The five ROM attribute-position codes are `name,size,crc,md5,sha1`. Name and size are sole claim text; three digest declarations use common `catalog_entry_hashes` with `hash_scope='whole_asset'` per fixture interpretation and no copied digest facts. A ROM is a child of its actual game, has one mixed game-child order, and uses the same ID as `catalog_media_entries`. The synthetic grammar's 14 recognized attributes all have one position row when present. The candidate does not claim authentic P/C support.

`clone` and `mergeof` are excluded from archive scalar columns and live in distinct marker/link owners. Their position rows reference the same `relationship_id` as the one canonical typed declaration (DAT `cloneof`/`cloneofid`, archive `clone`/`mergeof`, and synthetic-PC `clone`/`mergeof`); they do not copy target literals. A `P` clone marker has a NULL position relationship ID, checked against its typed marker owner, while non-marker clone declarations and all merge declarations require the ID. All seven native position ledgers have exact closed field codes matching the corresponding fields above; hash/NFO positions alone carry their unique reported declaration ID. Every attribute is singleton in this observed-compatible contract (`field_occurrence=0`); missing versus present-empty is position plus nullable text for ordinary text, or the shared hash presence state for digests. Repeated details/serials are rejected by the observed parser and each has `UNIQUE(actual_parent_id)`; repeated files and archive descriptions remain separate ordered elements. Do not interpret date/ID/flag/language/size-like strings as typed semantics beyond the documented checked size query projection.

Current-file hashes `crc32,md5,sha1,sha256` on both source and release files use common declaration rows with `hash_scope='unknown'`. Source-only `origin_sha256` uses `hash_scope='source_origin'`, distinct from current-file SHA-256; `origin_size` remains a separate source text field. These scopes are not whole-file matching evidence. Release-details `nfo_crc32` and `nfocrc` are separate NFO-companion declarations, `nfo_crc32`/`nfocrc` are not media hashes, and `nfo_size`/`nfosize` remain separate text values. Valid hash spelling derives from canonical hash bytes; empty is `presence='empty'`; accepted invalid text remains `presence='invalid'` plus an invalid subtype/diagnostic. Never create a file UUID from NFO or unknown/source-origin evidence.

Exports have one actual datafile root and at most one canonical header. `single_datafile` permits an absent header or a nested header before games; `sibling_header_datafile` requires one sibling header before the datafile. The document's independent `header_present` 0/1 fact is checked against canonical header existence (including a present-empty header) and mode; there is no second header count. Header fields always parent the canonical header. The nested placement row exists only in the first mode. Root-level games, nested header placement and their shared order come from the actual datafile root sequence; game-only rank is derived by subtracting one only when the header is nested. Each game's archive, dump-source and release rows share its mixed child order. Details, serials and files share the actual dump-source/release child order. No copied game ID or flattened media rank appears on descendant rows.

`catalog_sets.set_name` is the sole export game-name value. The name attribute's lexical order and QName location live only in `no_intro_export_game_field_positions`; `no_intro_export_games` carries neither a second name position nor a copied name value. Its row is limited to typed game identity and separately observed game extent.

The 18 edition count witnesses comprise ten owners (games, archives, dump sources/details/serials/files, releases/details/serials/files), header fields, and seven position totals (archive, dump details, dump serials, dump file, release details, release serials, release file). Per-game witnesses cover archives/sources/releases; per-source and per-release witnesses cover optional details/serials and files. Header presence is derived from one canonical header plus envelope mode, not a second boolean/count. The edition totals seal import completeness; per-owner counts support bounded page checks; neither substitutes for mixed-order uniqueness, actual-parent checks, or a full integrity scan.

## Indexes and checks delegated to the assembler

This file supplies typed-owner FKs, local singleton constraints, closed value/position enums, nonnegative order checks, positive observed coordinates, field-occurrence uniqueness, and parent/order/hash lookup indexes. `STRICT` prevents malformed SQLite storage classes without redundant `typeof` predicates. `candidate_no_intro_integrity_problems` provides concrete local checks for export envelope/header/conditional placement, physical-root extent/location containment when comparable complete ranges exist, 18 export edition count witnesses and nested game/source/release witnesses, and selected DAT/P-C requiredness/mode checks. The main assembler generates registry-kind, same-edition ancestry, owner completeness, mixed cross-table order, cross-family/XSI ordinal, and publication guards from the manifest. Required cross-table closures include: exactly one appropriate typed owner for each registry kind; one media base and one family payload for each media element; position presence exactly matching each accepted field; each hash position's reported ID matching owner/code/occurrence/edition; NFO invalid subtype iff invalid state; clone marker versus link exclusivity; and format-family/rules agreement.

`no_intro-hash-positions.tsv` is the exact candidate input mapping each media hash position table/owner/code/field/occurrence to its common declaration. It excludes release-details NFO hash fields, which are modeled separately and are not media declarations. The 16 rows cover four flat-DAT ROM hashes, three fixture ROM hashes, five observed source-file hashes, and four observed release-file hashes; source-origin SHA-256 occurs only on source files.

The bounded SQLite witness makes 18 assertions: one media/hash declaration per exercised family branch; exact hash-position links; NFO/media separation; nested and sibling canonical-header placement; null unknown root ends; unsigned-u64 fixture size retention; successful edition count closure in both export modes; rejection of a deliberately mismatched edition count; detection of nested-header extent escape; rejection of a placement inconsistent with envelope mode; detection of present-header deletion even when no header fields exist; absence of duplicate game-name position columns; rejection of NULL coordinate conventions on populated roots; relationship-position identity reuse; required DAT clone identity; wrong DAT clone identity; P-marker/link disagreement; and rejection of relationship IDs on non-relationship fields. It also runs three populated child/position query plans for archive-by-game, dump-file-by-source, and release-position-by-details access; each returned an indexed covering `SEARCH`. These are fixture checks, not corpus-wide or exhaustive branch/query proof.

The shared source hash table's closed field set is `crc,crc32,md5,sha1,sha256,origin_sha256`; `hash_values.algorithm` is `crc32,md5,sha1,sha256`. Check field-to-algorithm mappings (CRC/CRC32→crc32, etc.) and scope (`unknown`, `source_origin`, `whole_asset` only for synthetic fixture) in generated cross-family guards. No-Intro-reading editions reference the shared `catalog_reading_rules` via `catalog_editions.reading_rules_id`; candidate `format_family` values are `no_intro_dat`, `no_intro_database`, and `no_intro_pc_fixture`. Derive observed versus NUL-recovery interpretation from the edition reading rules and `catalog_xml_repairs.replace_nul`; do not copy a second recovery-mode value onto the export document.

The accepted policy leaves these gaps explicit: authentic DAT-o-MATIC P/C grammar is unsupported; export root/datafile complete interval capture and byte-to-coordinate mapping are not established by current parser observations; some DAT XSI parser-model facts (`source_qname`, resolved type identity) need capture while namespace context exists; flat-DAT candidate crosswalk records verifier omissions for release attribute positions and independent child-location checks; compatible DAT numeric-size projection bounds need an approved precise rule; parser-fed count/XSI publication evidence and every final query plan remain unproven; source/release hashes do not prove whole-file coverage. The nullable DDL shape reserves exact root diagnostic facts without inventing them. These are not reasons to drop accepted source fields from the relational mapping.
